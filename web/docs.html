Xinu ESP32-S3 - Documentacion completa del proyecto

Este documento cubre todo el proyecto: hardware, compilacion, kernel, dispositivos, red, sistema de archivos, JVM, aplicaciones Java, interfaz web y como extenderlo.

Vision general

Embedded Xinu es un sistema operativo pequeno y didactico. Esta portacion corre sobre ESP32-S3 y anade:

  • Driver de SD (SPI) + sistema de archivos FAT.
  • Red por W5500 (Ethernet) con pila TCP/UDP completa.
  • Pantalla TFT ST7735.
  • LED RGB discreto.
  • Boton.
  • Una JVM "Simple" que ejecuta clases Java compiladas, con librerias nativas para HW, IO, FAT, Sys, LVGL, Net y RGB.
  • Servidor HTTP en el puerto 80 con gestor de archivos y terminal web.
  • Servidor Telnet.

El kernel se ejecuta desde IRAM interna (128 KiB). El heap y las pilas viven en SRAM interna de datos (192 KiB). La PSRAM externa (8 MiB) se usa para buffers grandes, pilas de red y heap de la JVM.

Compilar y flashear

Requisitos

  • Toolchain Xtensa ESP32-S3 (xtensa-esp-elf-gcc).
  • esptool para flashear.
  • Python 3 con pyserial.
  • JDK para compilar las apps Java.

Compilar el kernel

cd /home/daniel/s3-xinu/compile
source ../env.sh
make PLATFORM=esp32s3 -j4

Genera compile/xinu.boot.

Flashear

esptool --chip esp32s3 --port /dev/ttyUSB0 --baud 460800 \
  write-flash --flash-mode dio --flash-freq 80m --flash-size 8MB \
  0x0 xinu.boot

Compilar las apps Java

cd /home/daniel/s3-xinu/jvm
./build-examples.sh

Las clases quedan en jvm/dist/java/ (apps) y jvm/dist/java/esp32p4/ (librerias nativas).

Sistema de build

El build se controla desde compile/Makefile y compile/platforms/esp32s3/.

  • platformVars: define APPCOMPS := shell apps mailbox network fs y DEVICES := tty uart-esp32s3 w5500 raw udp tcp telnet sd tft button rgb jvm memtty.
  • Makefile: si shell esta en APPCOMPS, define -DHAVE_SHELL=1.
  • Cada directorio tiene su propio Makerules que lista los .c a compilar.
  • Para anadir un nuevo .c: anadirlo a C_FILES del Makerules correspondiente y recompilar.
  • Para anadir un comando de shell: anadir xsh_foo.c a shell/Makerules, declararlo en include/shell.h y registrarlo en shell/shell.c dentro de commandtab[].

Agregar un nuevo .c

  1. Crear el fichero en el directorio adecuado, por ejemplo system/mi_modulo.c.
  2. Anadirlo a C_FILES en system/Makerules.
  3. Si es un driver, anadirlo tambien a DEVICES en platformVars y declarar el dispositivo en xinu.conf.
  4. Recompilar: make PLATFORM=esp32s3 -j4.

Ejemplo de Makerules:

C_FILES += memget.c memfree.c stkget.c ... mi_modulo.c

Modificar el Makefile

El Makefile principal incluye platforms/$(PLATFORM)/platformVars. Los cambios mas comunes:

  • Anadir un componente: modificar APPCOMPS en platformVars (por ejemplo, anadir test).
  • Anadir un driver: modificar DEVICES en platformVars.
  • Cambiar flags de compilacion: editar CFLAGS en platformVars o en el Makefile.
  • Cambiar el linker script: editar compile/platforms/esp32s3/ld.script.

El Makefile tambien define HAVE_SHELL y HAVE_TESTSUITE automaticamente segun APPCOMPS.

Linker script (ld.script)

El ESP32-S3 ejecuta el kernel desde IRAM interna. El script esta en:

compile/platforms/esp32s3/ld.script

Valores actuales:

iram (rwx) : ORIGIN = 0x40378000, LENGTH = 0x20000   /* 128 KiB */
dram (rwx) : ORIGIN = 0x3FCA8000, LENGTH = 0x28000   /* 160 KiB */

Si el enlazador dice region iram overflowed by N bytes, hay que liberar codigo: quitar comandos de shell, simplificar funciones o mover codigo fuera de IRAM. No se puede ampliar a 140 KiB porque la ROM carga mas bytes de los que admite.

Configuracion (conf.h / xinu.conf)

include/conf.h es un fichero generado. No se edita a mano. Se genera desde:

compile/platforms/esp32s3/xinu.conf

con compile/config/config. Define los numeros de dispositivo, los contadores (NTFT, NSD, etc.) y constantes de tamanio (NTHREAD, NSEM, etc.).

NETHER se define manualmente en xinu.conf porque el chip es W5500, no "ether".

Modelo de devices

Cada dispositivo se declara en xinu.conf con su tipo. El kernel mantiene una tabla devtab[] con punteros a funciones init/open/close/read/write/seek/getc/putc/control. El usuario abre un dispositivo con:

int dev = open(TFT0);   /* o open(CONSOLE, SERIAL0) */

Y lo usa con las funciones estandar:

control(dev, TFT_CTRL_CLEAR, TFT_BLACK, 0);
write(dev, "hola", 4);

Agregar un device nuevo

  1. Declararlo en xinu.conf: MI0 is mi on HARDWARE.
  2. Anadir el tipo de driver en DEVICES de platformVars.
  3. Implementar el driver en device/mi/ con miInit, miOpen, miRead, etc.
  4. Anadir el directorio a device/Makerules.
  5. Recompilar.

system/ en detalle

Los ficheros mas importantes de system/:

  • main.c: inicializa la consola, la pantalla, la red y arranca los servicios. Crea el shell serie.
  • kernel.c: inicializa el kernel, la memoria y las interrupciones.
  • thread.c: implementa hilos, el scheduler y el cambio de contexto.
  • memory.c: allocator del heap del kernel (memget/memfree).
  • semaphore.c / monitor.c: sincronizacion.
  • clock.c: temporizador del sistema.
  • psram.c / psramInit.c: gestion de la PSRAM externa.
  • xmalloc.c: allocator que usa PSRAM primero y heap interno como respaldo.

Shell

La shell es un hilo que lee de un dispositivo de entrada y escribe en uno de salida. Se registra en shell/shell.c dentro de commandtab[]. Cada comando es una funcion shellcmd xsh_foo(int nargs, char *args[]).

Limitaciones y ventajas

  • Ventaja: todos los comandos estan disponibles desde serie, Telnet y web terminal.
  • Limitacion: la shell es monohilo por consola. Un comando bloqueante (como java ColorShow) impide usar esa consola hasta que termine o se mate el hilo.
  • Los comandos de red dependen de que netup se haya ejecutado antes.
  • mem muestra el uso de memoria; free es mas detallado (heap, pilas, pools, PSRAM).

Sistema de archivos

Se usa FAT sobre la SD. El driver esta en device/sd/ y la libreria FAT en fs/. Se monta automaticamente al abrir SD0. Comandos clave: fat, ls, cd, pwd, cat, cp, mv, rm, mkdir, rmdir, head, tail, stat, hexdump, echo, df, du, xmodem.

Las rutas usan full_path() (definido en xsh_fs.h) para resolver rutas relativas.

Red

La red tiene varias capas:

  1. W5500 (device/w5500/): driver SPI del chip Ethernet. Expone ETH0.
  2. Ethernet (network/ether/): tramas Ethernet.
  3. ARP (network/arp/): resolucion de direcciones.
  4. IP (network/ip/): capa de red.
  5. UDP (network/udp/): datagramas.
  6. TCP (device/tcp/): conexiones fiables (buffer de 1024 B).
  7. DHCP (network/dhcpc/): configuracion automatica.
  8. DNS, HTTP, Telnet: servicios de aplicacion.

El arranque de red se hace en main.c con xsh_netup(1, {"netup", NULL}), que por defecto usa ETH0 y DHCP. Luego se arrancan telnetserver y httpd.

Nota importante: el buffer TCP es de 1024 bytes. La ventana inicial anunciada al peer debe ser igual o menor que ese buffer; de lo contrario el peer envia mas datos de los que caben y se corrompe el buffer. Por eso TCP_INIT_WND se define como TCP_IBLEN en include/tcp.h.

TFT / display

El display ST7735 se controla por el descriptor TFT0 con las funciones estandar:

control(TFT0, TFT_CTRL_CLEAR, TFT_BLACK, 0);
control(TFT0, TFT_CTRL_COLORS, TFT_WHITE, TFT_BLACK);
control(TFT0, TFT_CTRL_CURSOR, 4, 4);
write(TFT0, "Xinu ESP32-S3", 13);

El driver esta en device/tft/. La pantalla es de solo escritura (tftRead y tftGetc devuelven SYSERR).

JVM Simple

El proyecto incluye una JVM pequena ("Simple JVM") que ejecuta clases Java compiladas. El core esta en jvm/ (compartido con el build de host) y la adaptacion para el target en device/jvm/.

  • Soporta los bytecodes basicos y las extensiones del proyecto avanzado (0x78-0x82: ishl, ishr, iushr, etc.).
  • Las librerias nativas estan en jvm/lib/esp32p4/ (HW, IO, FAT, Sys, LVGL, Net, RGB).
  • Las apps estan en apps/java/.
  • El comando java <Clase> carga y ejecuta la clase desde /java en la SD.

Para compilar las apps: cd jvm && ./build-examples.sh. Las clases quedan en jvm/dist/java/.

SDK y librerias Java

Las librerias Java estan en jvm/lib/esp32p4/. Cada una declara metodos native que se vinculan con funciones C en device/jvm/native_*.c.

Ejemplo: RGB.java declara:

public static native void set(int r, int g, int b);
public static native void off();
public static native int get();

Y en device/jvm/native_hw.c estan las implementaciones esp32p4_rgb_set, etc., registradas en jvm/java_lib.c.

Apps Java

Las apps estan en apps/java/. Cada una tiene su propio Makefile. Las apps principales:

  • ColorShow: demo del LED RGB (bucle infinito).
  • RgbDemo: demo RGB.
  • DelayDemo: test de natives de HW.
  • LedBlink: parpadeo de LED.
  • ImgDemo, LvglDemo: demos de display.
  • Menu, WordQuest, Tetris: juegos/demos.
  • Args, Arr, Fields1, etc.: tests de la JVM.

Para ejecutar una app en la placa: java ColorShow (desde el directorio /java).

Crear nuevas librerias y natives

  1. Crear jvm/lib/esp32p4/MiLib.java con metodos native.
  2. Implementar las funciones C en device/jvm/native_*.c (o crear un nuevo fichero).
  3. Registrarlas en jvm/java_lib.c.
  4. Anadir el nombre a LIB_JAVA en jvm/build-examples.sh.
  5. Recompilar las apps con ./build-examples.sh.
  6. Subir solo las apps (.class) a /java en la SD, no las librerias (salvo que se quieran actualizar).

Interfaz web / file manager / terminal

El servidor HTTP en el puerto 80 (shell/xsh_httpd.c) sirve:

  • Ficheros estaticos desde la SD (incluido /index.html).
  • Un API en /api/ para el gestor de archivos (httpApiHandle en shell/httpapi.c).
  • Un terminal web en /webterm (usa MEMTTY0 y webterm.c).

La pagina index.html no esta en el kernel; es un fichero de la SD. Para actualizarla, copia el nuevo web/index.html a la raiz de la SD.

Subir ficheros a la SD

Desde la consola Xinu:

cd /java
wget http://<host>:8001/App.class App.class

O por XMODEM:

xmodem recv /java/App.class

Nota: wget funciona bien si la respuesta HTTP no supera el buffer TCP (1024 B total). Para ficheros grandes, el servidor envia en varios segmentos y el kernel los lee correctamente.

Problemas comunes

  • IRAM overflow: quitar comandos de shell o simplificar codigo. No ampliar a 140 KiB.
  • 0 bytes en wget: verificar que TCP_INIT_WND <= TCP_IBLEN en include/tcp.h.
  • ColorShow no para desde la consola: resetear la placa (el hilo JVM acapara la CPU).
  • Network: no link: verificar cable y alimentacion del W5500. La espera es de 5 s.
  • mem muestra heap negativo: bug corregido; usar free para datos fiables.
