Xinu · ESP32-S3

Embedded Xinu en ESP32-S3

Kernel propio, sin ESP-IDF y sin bootloader: la ROM carga la imagen en 0x0. Red real con W5500 por SPI2 hardware, FAT sobre microSD, pantalla ST7735 y una Simple JVM que ejecuta las clases del proyecto P4 sin recompilarlas.

Esta página se sirve desde la propia placa (httpd en el puerto 80) y vive en la microSD. El manual completo está en manual.html. La documentación extendida está en docs.html.

GPIO15 es del TFT. Es la línea de reset compartida entre la pantalla y el W5500. El driver del TFT la posee y la pulsa al arrancar; el W5500 usa reset por software (MR.RST) y nunca debe conducir ese pin, o borra la pantalla ya inicializada.

Memoria

El enlazador parte el mapa en IRAM y DRAM; la PSRAM se inicializa aparte y tiene su propio allocator. Las pilas de los hilos se colocan en PSRAM para no gastar SRAM interna.

Mapa

RegiónBaseTamaño
IRAM0x40378000128 KiB
DRAM0x3FCA8000160 KiB
PSRAM0x3C0000008 MB
Flash0x000000008 MB

Qué va dónde

  • IRAM: vectores, ctxsw, rutinas críticas y código marcado.
  • DRAM: tablas del kernel, globals, heap de memget.
  • PSRAM: pilas de hilo (stkget), buffers grandes, heap del JVM.
  • Flash: la imagen completa; no se ejecuta código desde PSRAM.

Pilas y allocators

ElementoValorUso
INITSTK4096 BHilos normales (shell, daemons); httpd usa 8192 B
JVM_STK65536 BHilo que ejecuta la VM y su recursión
NET_THR_STK2048 BRecepción de red y daemons ARP/ICMP
stkget—Pilas: PSRAM primero, SRAM como reserva
memget—Heap interno: mailboxes, estructuras pequeñas
psram_memget—Buffers grandes y estado del JVM
Regla práctica: nada de buffers de varios KB en la pila de 4 KB. Usa memget/psram_memget y libera con la misma longitud.

Arranque y build

No hay bootloader de ESP-IDF. La ROM carga la imagen en 0x0 y el start.S del port prepara la pila y salta a nulluser().

W5500 y pila de red

El W5500 está en modo MACRAW: solo mueve tramas Ethernet. ARP, IPv4, ICMP, TCP y UDP los implementa Xinu como hilos. El chip no hace offload de TCP/IP en este diseño.

Espera fuera del monitor. w5500Read y w5500Write hacen unlock() antes de sleep(1). Si durmieran con la llave del SPI, el httpd no podría transmitir y la red se pararía.
ARP aprendido del tráfico entrante. ipv4Recv llama a arpLearn() con la MAC del emisor antes de responder, para que el hilo de recepción no se bloquee resolviendo ARP.

Concurrencia

En Xinu no hay procesos con memoria separada: son hilos que comparten el espacio de direcciones. Por eso hacen falta mecanismos para no pisarse y para pasarse datos.

Los cuatro mecanismos

MecanismoQué es¿Lleva dato?¿Destinatario?Se bloquea…
SemáforoContador + cola de esperaNoNowait si el contador ≤ 0
MonitorSemáforo(1) + dueño + recursiónNoNo (solo dueño)lock si otro lo tiene
MailboxArray circular + 2 semáforos1 intNosend llena / receive vacía
send/receiveUn slot en thrtab[tid]1 intSí, tidreceive sin mensaje

Semáforo

semaphore s = semcreate(1);

wait(s);       /* --count; si <0, duerme */
/* sección crítica */
signal(s);     /* ++count; despierta    */

semcreate(1) = llave; semcreate(0) = evento; semcreate(N) = N recursos. count negativo = número de hilos dormidos.

Real: el pool de buffers de red (bfpalloc, bufget).

Monitor

monitor m = moncreate();

lock(m);       /* recursivo para el dueño */
buffer[idx] = dato;
idx++;
unlock(m);     /* al llegar a 0, despierta */

lock anidado solo incrementa count. unlock con count=0 devuelve SYSERR.

Real: ethptr->lock (SPI), s_fat_mon (FAT).

Mailbox

mailbox q = mailboxAlloc(8);

mailboxSend(q, (int)pkt);       /* bloquea si llena  */
pkt = (struct packet *)mailboxReceive(q);

No tiene destinatario: es la cola de un servicio. El dueño es el único que hace receive.

Real: arpqueue, icmpqueue.

Mensaje de hilo

send(tid, (message)pkt);   /* va al slot de tid */
msg = recvtime(1000);      /* 1 s; TIMEOUT si no llega */

Un solo slot por hilo. Si el destino ya tiene mensaje, send falla. Es punto a punto.

Real: reply de ping, aviso de ARP resuelto.

Semáforo(1) vs monitor

PreguntaSemáforo(1)Monitor
¿Sabe quién lo tiene?NoSí (owner)
¿Recursivo?No: el segundo wait duermeSí: count++
¿Sobre-liberable?Sí: dos signal dejan count=2No: unlock a 0 da SYSERR
¿Recuperable si muere el dueño?No hay forma de saberlomoncount() dice cuántos unlock faltan
CosteMínimo1 semáforo + entrada
La diferencia aparece cuando algo va mal: un signal de más, un lock anidado o un hilo que muere con la llave. El monitor está pensado para eso; el semáforo no.

Cuándo usar cada uno

Necesitas…Usa…
Exclusión sobre una secuenciaMonitor
Esperar un eventoSemáforo(0)
Contar recursosSemáforo(N)
Pasar trabajos a un servicioMailbox
Responder a un hilo concretosend(tid)

Reglas de oro

  • En un ISR: ni wait, ni sleep, ni lock, ni mailboxReceive.
  • Nunca duermas con un monitor cogido.
  • Un lock por cada unlock; si hay dos monitores, orden global.
  • No liberes monitor/mailbox/semáforo en uso.
  • Si el mensaje es un puntero, define quién libera la memoria.
  • Una mailbox por servicio, no por proceso.

Simple JVM

El port del proyecto P4 conserva los nombres esp32p4/* para que las clases compiladas en el P4 corran sin recompilar. La VM se ejecuta en su propio hilo con pila de 64 KB en PSRAM.

Pila del hiloJVM_STK = 64 KB
HeapJVM_HEAP_SLOTS = 2048 slots
MemoriaEstado y buffers en PSRAM
GCNo hay; evitar bucles que asignan sin parar
API de pausaesp32p4.Sys.sleep(ms)

Clases verificadas

  • java Loop
  • java StrBuild
  • java FloatTest
  • java ComplexDemo

Los ejemplos del P4 corren sin cambios. Sys.run() sigue comentado: no hay PMIC en el S3 y no se incluye esp32p4/PMIC.java.

Pendiente: Thread.sleep(long) apunta a un nativo que hace pop de un int; usa esp32p4.Sys.sleep(int) o corrige la firma. Tampoco hay GC real: los bucles largos que crean objetos acaban agotando el heap.

Gestor de archivos

Sube, descarga, borra y organiza ficheros de la microSD sin usar la consola. La API vive bajo /api/ y la sirve el mismo httpd del puerto 80.

Sin autenticación: cualquiera que llegue a la placa puede borrar ficheros. Úsalo solo en una LAN de confianza y no expongas el puerto 80 a Internet.

Terminal web

Ejecuta comandos del shell desde el navegador. El comando corre en el hilo webshell y su salida se captura con el dispositivo MEMTTY0; la página consulta el trabajo hasta que termina.

Sin autenticación: los comandos se ejecutan con privilegios de kernel. Cualquiera en la LAN puede lanzar reset, kill o borrar ficheros. No expongas el puerto 80 a Internet.
No interactivo: telnet, nc y xmodem necesitan una consola real. Tampoco se admiten redirecciones ni &. Los comandos largos se pueden consultar, pero todavía no hay botón de cancelar.

            xsh_httpd.c; WEBTERM_STK/WEBTERM_PRIO en
            webterm.c; SHELL_CMDSTK en include/shell.h.
    • 
        
  • Límite de comando: WEB_CMD_MAX en include/webterm.h y
            el buffer cmd de api_exec().
    • 
        
  • Página: edita web/index.html y súbela como index.new,
            luego rm index.html y mv index.new index.html.
    • 
      

    

  


  
Una conexión a la vez: httpd acepta, atiende y
     responde en serie. Después crea httpdRel para cerrar el socket sin esperar al FIN,
     pero dos peticiones simultáneas aún pueden recibir RST. El timeout de 2 s evita que una
     preconexión idle de Chrome bloquee el servidor. Sin autenticación: la API y el terminal
     ejecutan con privilegios de kernel; úsalos solo en una LAN de confianza.






  
Modificar el kernel

  
El árbol no usa git: haz un tarball antes de tocar nada. Cada directorio compila lo
     que declara en su Makerules.

  

    

      
Añadir un .c

      
    
        
  1. Crea el fichero en el directorio adecuado.
    2. 
        
  2. Añádelo a C_FILES en el Makerules de ese directorio.
    3. 
        
  3. Si es un directorio nuevo, añádelo a APPCOMPS o DEVICES en
            compile/platforms/esp32s3/platformVars.
    4. 
      

    

    

      
Añadir un comando

      
    
        
  1. shell/xsh_midemo.c con shellcmd xsh_midemo(int, char *[]).
    2. 
        
  2. Prototipo en include/shell.h.
    3. 
        
  3. Entrada en commandtab[] (shell/shell.c).
    4. 
        
  4. C_FILES += xsh_midemo.c en shell/Makerules.
    5. 
      

    

  

  

    

      
Añadir un dispositivo

      
    
        
  1. Driver con init/open/close/read/write/getc/putc/control.
    2. 
        
  2. Bloque de tipo e instancia en xinu.conf.
    3. 
        
  3. Directorio en DEVICES (platformVars).
    4. 
        
  4. No edites system/conf.c: es generado.
    5. 
      

    

    

      
Añadir un servicio al arranque

      
    
        
  1. En system/boot.c, añade una entrada a bootsvc_tab[].
    2. 
        
  2. wait = TRUE: corre en el hilo de arranque y bloquea el siguiente.
    3. 
        
  3. wait = FALSE: se lanza en su propio hilo.
    4. 
      

    

  

  

    
Configuración

    
Se edita compile/platforms/esp32s3/xinu.conf. De ahí se generan
       include/conf.h y system/conf.c.


#define NTHREAD   50
